# ADR 0004: RS256 access tokens with JWKS publication

- Status: Accepted (2026-09-29)
- Context: PLAN.md §5

## Context
User service issues tokens and the Gateway validates them. With HS256 both would hold the same secret, so a leak from either one lets an attacker mint tokens. Keys must be rotatable without downtime.

## Decision
- **RS256**. Only user-service holds the private key (`JWT_PRIVATE_KEY_PEM`, PKCS#8, from Secrets Manager `ecom/<env>/user/jwt` via ExternalSecret; `scripts/dev-keys.sh` generates one locally, and Compose uses `JWT_EPHEMERAL_KEY=true`).
- user-service publishes `/.well-known/jwks.json` with a `kid` per key. The Gateway uses `NimbusReactiveJwtDecoder.withJwkSetUri(USER_JWKS_URI)` over cluster DNS. This endpoint is not routed publicly. The keys are cached and refetched on an unknown `kid`, and the Gateway validates `exp`, `iss` and `aud`.
- Access tokens have a 15-min TTL and are not revocable. Refresh tokens are opaque, stored hashed, rotated on every use, and reuse of an old one revokes the whole family.
- Rotation: add the new key to the JWKS, sign with it (`JWT_KEY_ID`), and remove the old key after one access-token TTL.

## Consequences
- The Gateway holds only public material, so a compromised Gateway cannot mint tokens.
- JWKS availability matters at Gateway start and on rotation (it is cached otherwise). Compose orders startup with `depends_on: user-service: service_healthy`.
- Logout does not kill access tokens for up to 15 min. A Redis `jti` denylist is the post-MVP option.
